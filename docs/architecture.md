## Подход
Проект следует гексагональной архитектуре:
- **domain** — предметная модель и порты;
- **app** — use-cases/сервисы;
- **api** — HTTP-контракты (controller + DTO);
- **infra** — MongoDB-адаптеры и мапперы.

## Текущие модули

### Space
Ответственность:
- каталог процессов и их версий;
- каталог типов процессов (`ProcessType`);
- каталог типов операций (`OperationType`);
- валидация и ограничения целостности на уровне бизнес-правил.

Не делает:
- не считает estimate;
- не планирует выполнение;
- не хранит архив.

### Scheduler
Содержит несколько сценариев:
- estimate (виртуальный расчёт без сохранения) — реализовано;
- реальный план выполнения — в работе (MVP scope).

#### Scheduler: Plan (принципы реализации)
- вход в план — self-contained snapshot (без запросов в Space/Archive для доуточнения);
- single-writer на `planId` (запись в план только через command pipeline);
- write-команды обрабатываются приоритетными FIFO-очередями:
  - priority 1: `CHANGE` (изменения существующего плана),
  - priority 2: `APPEND` (добавление новой нагрузки);
- read (`GET`) обслуживается отдельно от write-очередей из актуального snapshot;
- write-события дедуплицируются по `eventId`.

#### Scheduler: Estimate
Ответственность:
- расчёт ожидаемого времени выполнения для входного набора items;
- построение виртуальных очередей по процессам;
- возврат детального результата расчёта в ответе API.

Не делает:
- не ставит сущности в реальный план выполнения;
- не сохраняет результат расчёта;
- не управляет архивом.

### Archive
Ответственность (MVP scope):
- хранение и выдача расчётов;
- хранение и выдача выполненных работ.

Контракт хранения расчёта:
- self-contained документ (input + result + metadata), без обязательного отдельного request-документа.

Статус: в работе.
