# Решения (ADR)

## Metadata
- Status: current (MVP decisions)
- Source of truth: принятые архитектурные/контрактные решения команды
- Last updated: 2026-02-04

## 1. processKey как уникальный ключ
**Статус:** принят  
**Причина:** нужен неизменяемый ключ для версий и ссылок из расчётов.  
**Следствие:** `processKey` задаётся на создание и уникален как идентификатор процесса; в БД уникальна пара `processKey + version`, `description` — только для отображения.

## 2. Версионирование процессов
**Статус:** принят  
**Причина:** расчёты должны ссылаться на конкретную версию процесса.  
**Следствие:** новое изменение — новая версия (v+1), а не перезапись.

## 3. Фильтрация через query‑params
**Статус:** принят  
**Причина:** стандартный REST‑подход для коллекций и проще расширять.  
**Следствие:** `GET /api/v1/space/processes` поддерживает `type` как query-параметр фильтра.

## 4. Листинг только latest-версий процессов
**Статус:** принят  
**Причина:** основной клиентский сценарий использует актуальные версии; полный список версий должен запрашиваться отдельно.  
**Следствие:** `GET /api/v1/space/processes` возвращает latest по каждому `processKey`; история версий доступна через `GET /api/v1/space/processes/{processKey}/versions`.

## 5. rateOptions вместо единого rate
**Статус:** принят  
**Причина:** для процесса есть фиксированные варианты скорости для типовых сценариев выполнения.  
**Следствие:** процесс хранит список `rateOptions`, выбор варианта обязателен.

## 6. Batch volume обязателен для процесса
**Статус:** принят  
**Причина:** в MVP расчёты и планирование используют batch-логику, отдельный режим handoff не нужен.  
**Следствие:** `batchVolume` обязателен (`> 0`) в `ProcessCreateRequest` и `ProcessNewVersionRequest`.

## 7. OperationType immutable в MVP
**Статус:** принят  
**Причина:** чтобы не допускать скрытых переименований и расхождений справочника операций.  
**Следствие:** в MVP нет rename/update для `OperationType`; повторный `create` с тем же `type+processType` даёт `409 Conflict`, а попытка передать другую версию данных трактуется как запрещённый update через create.

## 8. Estimate как виртуальное планирование без сохранения
**Статус:** принят  
**Причина:** в Scheduler нужны разные режимы; estimate нужен как быстрый расчёт без побочных эффектов.  
**Следствие:** `POST /api/v1/scheduler/estimate`:
- принимает полный входной набор данных;
- строит виртуальные очереди и возвращает результат;
- ничего не сохраняет в БД и не изменяет состояние;
- реальный план и архив реализуются отдельными сценариями.

## 9. Выбор скорости в estimate через rateSelection (XOR)
**Статус:** принят  
**Причина:** нужен явный и однозначный контракт выбора скорости без двойной трактовки.  
**Следствие:** `ProcessSelectionRequest` использует:
- `rateSelectionMode = OPTION` + `selectedRateOptionKey`, либо
- `rateSelectionMode = OVERRIDE` + `rateOverride { units, minutes, reason }`.

Пейлоад с обоими/ни одним вариантом отклоняется с `400`.

## 10. Каноничная формула времени процесса item
**Статус:** принят  
**Причина:** исключить двойной учёт setup и неоднозначность в коде/доках/API.  
**Следствие:** используется формула:
- `estimatedMinutes = setupMinutes + productionMinutes`,
- где `productionMinutes` — сумма изготовления всех batch без setup.

## 11. Архив расчёта хранит self-contained документ
**Статус:** принят (контракт)  
**Причина:** при повторном запуске/аудите нельзя зависеть от отдельного request-документа или восстановлений из внешних источников.  
**Следствие:** документ архива расчёта хранит:
- `input` (нормализованные данные, включая `versionUsed` и `rateSelectionUsed`);
- `result` (итог расчёта и очереди);
- метаданные (`calculationId`, `calculatedAt`, `algorithmVersion`).

Это позволяет сохранять/читать расчёт как один самодостаточный объект.
